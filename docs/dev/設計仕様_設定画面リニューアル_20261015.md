## 0. 目的と範囲

**成功状態**：設定を開くと「何がどこにあるか」が1画面で分かり、押した先で迷わず、保存したかどうかを毎回同じ見え方で判断でき、拡大表示でも読める。

**問題の3層**

| 層 | 内容 |
|---|---|
| 根っこ | 設定ページ（個人）と AdminView（管理）が別々に作られ、目次・ヘッダー・保存・未保存確認をそれぞれ持つ |
| 中間 | 項目名が内容を表さない（「通知」2か所・「グループ・部署」）／保存方式が項目ごとに違う／管理側だけ文字を縮める小中大がある |
| 表面 | 目次の二重・10〜12px の文字・狭い余白・窮屈なヘッダー |

**やること**：トップのカード化／詳細ページの共通枠／名称の付け直し／保存と未保存確認の統一／見た目の数値基準／3段階リリース。
**やらないこと**：AdminView 内部の業務ロジック・DB・RLS・Edge Function の変更／各管理機能の仕様変更（OKR・PJ・メンバー等の中身）／新しい設定項目の追加／ガイド記事の全面書き直し（文言の追従のみ）。

## 2. 画面の型

### 2.1 トップ

- 見出し（13px・太字）→ カードのグリッド。PC は `repeat(auto-fill, minmax(260px, 1fr))`、モバイル（幅768px以下）は1列の行型（右端に「›」）。
- カード全体が1つの `button`。Enter／Space で開く。フォーカスリングは常に出す。
- 詳細から戻ったとき、トップのスクロール位置を復元する（ref に保持）。

### 2.2 詳細ページ

- **見出しバーを1本にする**：左に「← 設定」（トップでは出さない）、続けてページ名、右に「？」と「✕」。現在 `MainLayout` の adminOverlay が持つバー（⚙ 設定・？・✕）を `SettingsView` 側へ移し、トップではタイトル「設定」だけを出す。右端は `withBellReserve` を維持する。
- 本文の先頭に、そのページの説明（12〜13px・1〜2行）。部署に依存する7ページ（Objective・KR／Task Force・ToDo／プロジェクト／メンバー／メンバータグ／プロジェクト招待／AI使用量）では、表示部署が2つ以上のとき「🏢 編集対象：◯◯」のチップを説明の横に出す。
- **目次は置かない**。階層が「トップ→詳細」の2段だけのため、パンくずも作らない。戻る手段は「← 設定」の1つ。
- 詳細ページは離れるとアンマウントする。現行の「管理を一度開いたらマウントしたまま隠す」は廃止する（未保存確認を一本化するため。3.3）。

### 2.3 PC とモバイル

| 項目 | PC | モバイル（幅768px以下） |
|---|---|---|
| トップ | 多列グリッド | 1列の行型 |
| 見出しバー | 「← 設定」＋ページ名 | 「‹ 設定」＋ページ名（文字は省略せず折り返す） |
| 本文の幅 | 個人ページ 最大720px／管理ページ 最大960px | 全幅（左右16px） |
| 管理ページ内の表 | そのまま | 横スクロール（現行どおり） |

高倍率の拡大では CSS px の幅が縮み、自動的にモバイル型へ切り替わる。意図した挙動とする。【未確認】Teams 埋め込み（iframe）での切替位置は実機で確認する。

### 2.4 ブラウザの戻る

【確認済み】アプリは `pushState`／`popstate` を一切使っておらず、ガイド・ラボ・設定はすべて画面内の状態で切り替えている。【設計】設定だけ履歴に載せない（理由：①他の全画面と挙動が揃う ②戻るで離れるときの未保存確認は、履歴が先に動いてから巻き戻す処理が要り事故りやすい）。段階3で利用者の声があれば再検討する（論点②）。

### 2.5 検索欄

【設計】**付けない**。理由：①カードは最大18枚で、PC 100% なら1〜2画面で全体が見える ②「見つからない」の主因は二重目次と項目名の曖昧さで、名称変更と1行説明で解消する ③検索を足すと細項目の索引が別に要り、項目追加のたびに更新漏れが起きる（Section 65 の置き場問題の再来）。再評価の条件は「カードが20枚を超える」または「探せないという声が出る」。

### 2.6 直接ジャンプ（維持する入口）

ページ ID を1つの型 `SettingsPageId`（18値）に統一し、`openSettings(pageId?)` に一本化する。

| 入口（現行） | 新 |
|---|---|
| 歯車（PC サイドバー／モバイルヘッダー） | トップ |
| ダッシュボード・ベルの「通知設定」（`app:open-settings` detail=`notify`、`onOpenSettings`） | `notify` |
| `/?open=admin-errors` | `errors` |
| `/?open=admin-backup` | `backup` |
| `/?open=admin-sent` | `messages` |
| `/?open=admin-message&mid=…` | 変更なし（設定は開かず、お知らせの詳細だけを重ねる） |
| オンボーディングの CTA（`OnboardingHome.onOpenAdmin`） | 現行は「未設定が大きい領域」を自動選択。新構造では呼び出し元が `okr` または `pj` を明示 |

- 権限のないページ ID が来たらトップを開く（現行の「🔒 管理者のみ」画面は直接ジャンプでしか出ないため廃止し、トップへ寄せる）。
- ゲストには設定を出さない（`!isGuest` のガードと `(isAdminOpen && !isGuest)` を維持）。
- `AdminView` の `initialTab` と `SettingsView` の `initialSection` は `initialPage` に置き換える。

## 3. 保存の統一ルール

### 3.1 基準（1つ）

**「入力の途中状態が生まれるか」で決める。**

- 生まれない（トグル・選択肢・色・1回の操作で値が確定する）→ **即時保存**。
- 生まれる（文字・数値・日付の入力、複数欄を組にして保存する、パスワード）→ **保存ボタン**。
- 同じフォームに入力途中の欄が1つでもあれば、そのフォーム全体を保存ボタンにする（混在させない）。
- 設定値を持たない操作（削除・取り消し・送信・初期化・バックアップ実行・テスト送信・ログアウト）は「保存」ではなく**実行**とし、確認ダイアログまたは結果のトーストで扱う。

### 3.2 全項目への当てはめ

| ページ | 項目 | 型 |
|---|---|---|
| プロフィール | 表示名・短縮名・色（1フォーム） | 保存ボタン |
| アカウント | パスワード変更 | 保存ボタン |
| アカウント | ログアウト | 実行 |
| 表示 | テーマ・言語・一覧の表示密度 | 即時 |
| 表示 | サイドバー幅を既定に戻す | 実行 |
| 通知の受け取り方 | 知らせ方・通知する内容の表・送信時刻 | 即時 |
| 通知の受け取り方 | 許可・このブラウザの登録・テスト送信 | 実行 |
| 困ったとき | 再読み込み・ガイド・ツアー・ショートカット・更新履歴 | 実行 |
| 困ったとき | 表示の設定を初期化 | 実行（確認ダイアログ・danger） |
| 困ったとき | 自部署の管理者 | 表示のみ |
| Objective・KR | 目標の入力／KR の追加・編集 | 保存ボタン |
| Task Force・ToDo／プロジェクト／メンバー／メンバータグ／部署 | 追加・編集フォーム | 保存ボタン |
| 上記5ページと Objective・KR | 削除・Q 移動・解除・PDF 取込 | 実行 |
| プロジェクト招待 | 取り消し | 実行（確認ダイアログ） |
| AI使用量 | 集計表示 | 表示のみ |
| お知らせの送信 | 作成フォーム | 保存ではなく「送信」ボタン（確認ダイアログ付き・現行どおり） |
| ローディングのヒント | 編集フォーム | 保存ボタン |
| ローディングのヒント | 上下の並べ替え | 即時 |
| ローディングのヒント | 削除・初期に戻す | 実行（確認） |
| バックアップ | 今すぐ実行・ダウンロード | 実行 |
| 期限リマインドの実行状況 | 今すぐ実行（dryRun） | 実行（記録は残さない） |
| 利用者の画面のエラー | 解決済み／未解決の切替 | 即時 |
| 利用者の画面のエラー | 「未解決のみ」絞り込み | 保存しない表示条件 |

### 3.3 未保存確認を Section 46 に一本化する

- 【確認済み】現行は2系統。SettingsView は `confirmDiscardUnsavedEdits`（プロフィール・パスワードの2か所だけ登録）、AdminView は独自の `isDirty` と `confirmDialog`（「タブを切り替えると変更は失われます」）。
- 【設計】新設の共通フック `useUnsavedEditor(isDirty)`（`src/hooks/`）が、`useId` と ref による登録・解除をまとめる（登録の書き忘れとコピペを防ぐ）。プロフィール・パスワード・AdminView のルートが使う。
- AdminView は既存の `isDirty` state を、ルートで上記フックに渡すだけにする。各セクションの `onDirtyChange` は触らない（4000行を壊さずに統一できる）。AdminView の `changeTab` の独自確認と `setIsDirty(false)` は、タブ切替自体がなくなるため削除する。
- 設定内の遷移（カード→詳細／← 設定）は、`SettingsView` 内の `guardedSwitch`（`PersonalOkrView` と同型）だけを通す。文言と安全側の既定は Section 47 のまま（背景クリックは「編集に戻る」）。✕・ナビ・ログアウトは既存の `guardedNavigate`／`handleLogout` が受ける。
- 新ルール：設定ページ内の状態遷移は `guardedSwitch` 経由に限る。ソース走査テスト（`guardedNavigateCoverage` の対象に SettingsView を追加）で固定する。

### 3.4 保存できた・失敗の見せ方

| 型 | 成功 | 失敗 |
|---|---|---|
| 即時 | 操作した欄の横に「✓ 保存しました」を1.5秒（12px・success 色）。トーストは出さない | 値を操作前に戻し、トースト（error・`formatErrorForUser`） |
| 保存ボタン | ボタンが「✓ 保存済み」に戻る（disabled・cursor default）。トーストは「保存しました」を1つ | フォーム直下に永続のエラー帯（Section 15・45）。入力は保持 |
| 実行 | 結果をトースト1つ（success／error） | 同左 |

保存ボタンの状態は3つに固定する。**未変更**＝「✓ 保存済み」(disabled)／**変更あり**＝「保存」(活性)＋左に「未保存の変更があります」(12px・warning 色)／**保存中**＝「保存中…」(disabled・cursor wait)。🚫 の禁止カーソルは使わない（Section 48）。追加フォームの文言は「追加」、送信は「送信」。単一行入力の Enter と Ctrl／Cmd＋Enter で保存する（IME 変換確定の Enter は無視。Section 44）。

## 4. 見た目の基準

### 4.1 基本方針

- 【確認済み・Section 60】`fontSize` を下げる方向の調整は行わない。設定画面の最小文字サイズは **12px**（現行の10・11px は廃止）。
- 色・角丸は既存の `var(--color-*)`／`--radius-sm 6px`・`--radius-md 10px`・`--radius-lg 16px` を使う。ハードコードしない。
- px 指定のままとし、拡大はブラウザに任せる。CSS `zoom` プロパティは使わない（現行の小中大が使っている）。

### 4.2 数値（PC／モバイル）

### 4.3 管理ヘッダーの3要素

## 7. 決めてほしい論点（推奨つき）

1. **管理ヘッダーの文字サイズ「小中大」を廃止してよいか。**
   推奨：**廃止**。拡大して使う利用者への対応は、基準サイズの引き上げ（本文14px・補助12px以上）とブラウザ拡大で行う。残す場合の代案は「表示」ページへ移し、小（0.85倍）を外した2段階（標準・大）にする。

2. **ブラウザ・スマホの「戻る」で設定の中を戻れるようにするか。**
   推奨：**段階1・2では対応しない**。画面上の「← 設定」で戻る。他の全画面と挙動が揃い、未保存確認との競合が起きない。モバイルで戻るボタンを押して設定ごと離れるという声が出たら、段階3で履歴対応を設計する。

3. **段階1で AdminView の中身（文字・余白・文言）を旧来のままにして構造だけ先に出してよいか。**
   推奨：**よい**。段階1の時点では、管理ページの本文は旧い見た目（10〜12px）でカード・枠だけが新しくなる。段階2で本文が追従する。1回で全部を出す案は、4000行の AdminView に見た目・保存・名称の変更が同時に入り、不具合の切り分けができなくなる。
