# 教訓集（lessons-learned）

このアプリの開発・運用で実際に起きた事故から、再発防止に効く事実だけを短くまとめたもの。ルールの強制ではなく、判断材料として置く。
グランドルールとして CLAUDE.md に昇格済みのものは節番号を添えた。

## 1. Supabase・DB

- **列を空にする（解除する）ときは `null` を送る。`undefined` を送らない。** postgrest-js は本文を `JSON.stringify` するため、値が `undefined` のキーは丸ごと消え、その列は更新対象から外れる。「保存したのに反映されない」「解除が効かない」という無反応バグになる。空にできる列の型は `string | null` にする。
- **複数の関数を含む SQL では、ドル引用のタグを関数ごとに変える（`$fn_group_id$`・`$fn_guard$` など）。** すべて `$$` だと、貼り付けで1文字欠けたときに後続の関数まで文字列として飲み込まれ、遠く離れた行で構文エラーになり原因を特定できない。大きなマイグレーションはブロックに分けて貼り、失敗時にブロック単位で再実行できるようにする。本体にシングルクォートが無い SQL 関数なら、ドル引用を使わず通常の文字列リテラルにする手もある。
- **マイグレーションを伴う変更は、本番コードの反映（main への push）と本番 DB への SQL 適用の時間差で壊れる。** 例：新しい列を書きに行くコードが先に本番へ出て列がまだ無いと、タスク保存が全滅した（`upsertTask` が Task 型の全フィールドをそのまま送るため、型に列を足すと保存ペイロードに自動で入る。読み取りは `select *` なので無事）。可能なら SQL を先に適用してから push する。Vercel の自動デプロイ運用でそれが難しいときは、push 直後に即適用する。
- **本番へのデプロイ経路**：main へ push すると Vercel が本番へ自動デプロイする。Supabase のマイグレーションと Edge Function は push では反映されない。
- **開発 DB（dev）と本番 DB は構造がずれる（drift）。** 列を足した後は、実装の前に `information_schema.columns` で実在を確認する。`schema.sql` を信じない（CLAUDE.md Section 22・58）。

## 2. Edge Function と AI 呼び出し

- **546 `WORKER_RESOURCE_LIMIT` は、サイズでも実行時間でも出る。** Supabase には関数ごとにメモリ・CPU・実行時間の上限を上げる設定が無い。効いた順に、①AI 呼び出しを分割して1回を短くする ②入力をクライアント側で集計して絞る ③`max_tokens` を下げる ④速いモデルにする ⑤大きな添付は base64 で送らずクライアント側でテキスト抽出する。「しばらく経ってから546」なら時間、「即座に546」ならサイズが切り分けの目安。AI 中継の Edge Function は、設計時から「1回の呼び出しを短く保つ」を要件にする（Section 28 に実例）。
- **`supabase.functions.invoke` が非2xxを返すとき、`data` は `null`。** Edge Function が返した理由は `error.context`（Response）にあり、`await context.json()` で読む。`data` だけ見ていると、丁寧に書いたエラー分岐が一度も実行されず、利用者には汎用文言しか出ない（数日、原因不明が続いた実例）。関数を呼ぶコードを書いたら、わざと失敗させて原因が読めるか確認する（Section 15・26）。

## 3. フロントエンド

- **zustand（v5）のセレクタが、呼ぶたびに新しい配列・オブジェクトを返すと、React error #185（Maximum update depth exceeded）で全画面がクラッシュする。** `.filter()`・`.map()` を素のまま `useAppStore(selector)` に渡すと、状態が変わっていなくても毎回「変化した」と判定される。tsc・vitest・eslint はすべて通り、本番デプロイ後に初めて落ちた実例がある。対処は、セレクタを「同じ state に同じ参照を返す」ようメモ化する（`appStore.ts` の `memoizeScopedSelector`）か、呼び出し側を `useShallow` で包む。参照の同一性を直接検査する単体テスト（`src/stores/__tests__/scopedSelectors.test.ts`）が核心を捕まえる。zustand 周りを触る変更は、静的検査だけでは足りず、実画面でコンソールエラーが無いことを確認する。
- **`useT()` の戻り値を、`useEffect`・`useCallback` の依存配列に入れない。** 描画ごとに新しい関数が返るため、取得処理が描画のたびに再実行され、通知ベルの取得ループ（v3.133）を起こした（Section 69）。
- **JavaScript の文字列デリミタに全角の引用符（U+201C / U+201D）を使わない。** 日本語を含む文字列を書くときに混入すると、スクリプト全体が SyntaxError で止まり、「ヘッダーだけ表示されて中身が空」になる。診断は、コードポイントのスキャンと `node --check`。
- **`public/` に置いたファイルは、認証を通らない公開 URL になる。** アプリがログインを要求していても、ビルド後の `public/` 配下の静的ファイルは未ログインで取得できる。社内情報（テナント名・社用メールアドレスなど）を含むファイルは `public/` に置かず、非公開の Storage バケット＋`authenticated` のみ許可する RLS など、既存の認証と同じ強さの配信経路を使う。
- **出現アニメーションは、サイズ・位置が実際に大きく変わる形にする。** 不透明度＋小さな平行移動（16px 程度）だけでは「動きが無い・弱い」と受け取られる。既存の評価の高い参照パターン（AI 相談パネルの幅 0→実幅、カンバンカードのホバー）と同程度の視覚的な変化にする。
- **新しい外部ライブラリ（npm など）の導入は、外部サービスの利用と同じに扱う。** ローカルで動くことは安全を意味しない。ライブラリ自体が使用統計を外部送信することがある。導入前に外部通信・データ収集の特性を確認し、既存の実装で代替できないかを先に検討する。このアプリは外部チャートライブラリを入れず、インライン SVG で描く方針（`.claude/skills/taskmanage-dataviz-widget/`）。

## 4. 通知・外部連携

- **外部の接続先（Power Automate など）に依存する通知は、黙って止まる。** 旧 Teams 通知は、フロー所有者と投稿用の接続が個人に紐づいており、その人が投稿先に入れなくなって止まった。受け口は受信時点で 202 を返すため、送信側からは成功に見え、誰も気づかなかった。再発防止は、送信結果を DB に記録し、管理画面で見えるようにすること（`web-push-reminder-design.md`、Section 58）。
- 同じ経路に依存している別機能（バックアップの失敗通知）も同時に止まっていた。**1つの外部経路を直すときは、同じ経路を使う他機能を洗い出す。**

## 5. テストと検証

- **再発防止のテストは、修正前のコードで実際に赤くなることを確認してから採用する。** あわせて、検査対象を「ソースの書き方」でなく「成立してほしい結果」に張る。実例：モーダルの上端が画面外に切れて入力欄に届かない不具合は、一度直され、機械チェックも書かれたのに再発した。検査が1経路（`alignItems:"center"` の文字列一致）しか張られておらず、同じ結果に至る別経路（CSS アニメーションの `animation-fill-mode` で残る `transform`、三項演算子で書かれた別形）が素通りしたため。「守りたい結果」を1文で定義し、壊れる経路を複数数え、文字列一致の検査は三項・変数経由・定数化・スプレッドなど同義の別表現が素通りしないかを自問する。同じ挙動をコピーして実装している箇所は、1つだけ改良されて他が取り残されるので、最もよくできた実装との差分を取る。「〜と同じ方式」というコメントは根拠にせず、参照先の実物を読む（Section 21・59）。
- **件数の一致は、欠落と重複の相殺を検出できない。** 取り込み漏れ（−）と重複登録（＋）が同じ区分で起きると打ち消し合う。基準線は全件リストの名前単位の diff で一度確定し、件数だけの照合はその後の変化の監視にだけ使う。完了報告は「N 件完了」の文面でなく、依頼した各件が実在するかを1件ずつ確認する。判定表の「一致」は「件数のみ一致」と書く。
- **既定値・初期状態・表示条件を変える前に、現状の挙動をコードで確認する。** 「たぶんこう動いているはず」で安全側に倒すと、既にあった便利な挙動を殺す。実例が2回ある：サイドバーの完了 PJ の扱い（元の実装は `status === "active"` のみを通していたのに逆方向へ変更した）、PJ 引き継ぎ時の日付（`dateSlide.ts` が元 PJ 開始日→新 PJ 開始日の相対日数を常に保って引き継いでいたのに、既定をオフにした）。読む余裕が無いときは「まず現状を確認して報告してから実装する」を指示に入れる。
- **配布物の「初回だけ走る処理」は、引き渡し前に、初回の状態で丸ごと1回通す。** 開発環境では完了マーカーが既にあり、初回経路が一度も実走していないことが多い。ファイルを別フォルダへ移したときは、相対パス参照と、呼び出し側の作業ディレクトリ前提を突き合わせる。失敗経路（中断メッセージ）も、成功経路と同じく一度は実際に表示させる。失敗メッセージの原因候補は断定しない。

## 6. 開発の進め方

- **コミットを分割するなら、各コミットのツリーで `npm run build` を通す。** Vercel は main の各コミットをビルドするため、中間コミットがビルド不能だとそのままエラー通知になる（HEAD が健全でも）。ファイルを手で選んで版に振り分ける方式は、中間ツリーの破損に気づけない。「分離しきれない」と感じた時点が分割をやめる判断点で、その場合は1本にまとめる。検証は `tsc --noEmit` だけでなく `npm run build` で行う。
- **同じチェックアウトで複数のセッションを同時に動かさない。** 片方の未コミットの作業ツリーがもう片方に混入し、ビルドが壊れる・他方の変更が退避される事故が起きた。作業前に `git status` で、自分のタスクと無関係な大量の未コミット変更が無いか確認する。他者の未コミット変更に `git stash` を使うなら、必ずファイルを指定する（`git stash push -- <files>`）。stash した後は `git stash list` で残っていないか確認する。他人の未完成の機能を代わりに commit・push しない。
- **着手の有無は git の痕跡だけで判断しない。** 読み取り段階では痕跡がゼロなので、同じ依頼を二重に発注し、`version.ts`・`CLAUDE.md`・`CHANGELOG.md` で衝突した。これらの共有ファイルを触る作業は並走させず直列にする。

## 7. 運用

- **「ログインできない」という問い合わせは、まず Auth のメールと `members.email` が一致しているかを確かめる。** 自動ログイン（`App.tsx` の `autoMatch()`）は両者の一致で本人を特定する。一致しないと、ログイン自体は通ってもメンバーとして認識されず、通常画面に入れない。実例は、メンバー登録と違うアドレス（個人の Gmail など）でアカウントを作っていたケース。比較では大文字小文字・前後の空白を無視する（Section 76）。
- **Supabase CLI・`pg_dump` など、外部クラウドへ接続・操作するコマンドは、社内のセキュリティ監視（EDR）で検知され、ヘルプデスクから照会が来た実績がある。** 読み取りだけの照会も対象になった。実行は人が行っている。
