# 企画提案：アプリ内フィードバック（利用者の声を、場面つきで10秒で送れるようにする）

- 作成日：2026-10-15　対象：task_manage v3.155　状態：**案（山本さんの合意前。実装は合意後に developer）**
- 着手の前提：設定画面リニューアル（`設計仕様_設定画面リニューアル_20261015.md`）とリスト改善の実装が終わった後。
- 記号：【確認済み】コードで確認した事実／【設計】本書で決める内容／【未確認】実機・本番でしか確かめられない点
- ワークフロー型：AIワークフローではないため Building Effective Agents の型の特定は不要。将来、受信の分類・重複まとめにAIを使う場合は「ルーティング」の最小形から始める（本計画の範囲外）。

---

## 0. 目的と範囲

**成功状態**：利用者が「ここが使いにくい」と思った瞬間に、コメントだけで送れる。管理者は、どの画面で・何をしていたかを再現情報つきで受け取り、そのまま Claude に貼って改修に進める。

**問題の3層**

| 層 | 内容 |
|---|---|
| 根っこ | 要望・気づきが口頭やチャット経由で届き、再現条件（画面・操作・表示設定）がその場で失われる |
| 中間 | エラーは自動収集（Section 67）できるが「エラーにならない不満・改善要望」を拾う入口がない。お知らせ（Section 68）は一方通行 |
| 表面 | 受けるたびに「どの画面ですか」「拡大率は」と聞き返す。送る側は書く場所を探して諦める |

**やること**：送信入口／一言フォーム／スナップショットの自動添付とプレビュー／super_admin への通知と管理一覧／Claude 貼り付け用コピー／送信者への状況の見える化。
**やらないこと**：画面の画像の取得／タスク名などの業務データの自動添付／投票・コメントの掛け合い（掲示板化）／AIによる自動分類／外部サービス（Slack・Teams 等）への転送／部署管理者への公開（論点2）。

判断基準：既存の仕組み（`client_error_logs` の RPC 型・レジストリ・errorCopyText・設定画面）に載せ、新しい部品を最小にする。

## 1. 送る側の体験

### 1.1 入口の候補比較

| 候補 | 利点 | 難点 | 判断 |
|---|---|---|---|
| A ベルのパネル上部（「⚙ 通知設定」の隣に「💬 ご意見を送る」） | 全画面・PC／モバイルで常に見える。追加の固定要素が要らない。返信・状況の見え方も同じ場所に置ける | 「ベル＝通知」の連想から外れる | **推奨（主）** |
| B 設定「困ったとき」ページのカード | 「困ったらここ」（Section 65）と一致 | 設定を開く手間が1段増える | **併設** |
| C エラー表示（ErrorBar・ErrorBoundary）の横の「この状況を報告」 | 直前のエラーが自動で紐づき、不具合報告の質が最も高い | エラーが出た時しか使えない | 段階2 |
| D キーボードショートカット | 慣れた人が最速 | ブラウザ予約キーとの衝突確認が要る【未確認】 | 段階2 |
| E 右下の常設ボタン | 目立つ | 右下スタックは重なり・切れの事故が3回（Section 43・49・50）。常設要素を増やさない | 不採用 |
| F サイドバー「その他」 | 既存の置き場 | 既定で折りたたみ（Section 32）。モバイルで導線が弱い | 不採用 |

ゲストには出さない（Supabase に接続しない設計＝Section 23。RPC 側でも拒否）。

### 1.2 送信フォーム（目標：10秒）

操作は「ベルを押す → 💬 を押す → 一言書く → Ctrl/Cmd+Enter」の4手。

- モーダル1枚（Section 21 の `modalStyles.ts`）。一言コメント（必須・1,000字まで・文字数表示）。
- 種類は任意の3択チップ（要望／不具合／その他）。未選択のまま送れる（未選択は「未分類」で保存）。
- 「画面の状況を付ける」チェック（既定オン）。その下に「送る内容を見る」（折りたたみ。2.3 参照）。
- 注意書き1行：「社外秘・個人情報は書かないでください」。
- 入力中に画面遷移しようとしたら Section 46 の未保存確認の対象にする（`useUnsavedEditor`）。
- **スナップショットはモーダルを開いた瞬間に確定する**（開いた後の画面・クリックを含めない。ベル・モーダル自身のクリックは履歴から除く）。

### 1.3 送信後の見え方

- 成功：モーダルを閉じ、トースト「送信しました。ありがとうございます」。
- 失敗：入力を保持したまま、フォーム直下に永続のエラー帯（Section 45・15）。頻度上限に当たった場合は理由を文言で示す。
- モーダルの「送った内容と状況」タブで、自分の送信一覧を見られる（本文・日時・状態。管理者のメモは見せない）。

## 2. スナップショットの中身

### 2.1 軸の考え方

山本さんの案どおり、**画像ではなく構造化データ（コード・座標）で再現できる情報**を軸にする。送る値は「列挙値・数値・ID・要素の種類」に限り、**画面に表示された文字列（タスク名・PJ名・コメント・検索語）は一切含めない**。構築は許可リスト方式の純関数（任意の DOM や state を丸ごと直列化しない）。

### 2.2 採否表

| 候補 | 価値 | 漏洩リスク | 判断 |
|---|---|---|---|
| 画面名（`getClientErrorScreen`） | 高 | なし | **既定で付ける** |
| ビュー・モード（リスト／ガント／カンバン、計画／OKR、設定のページ） | 高 | なし | **付ける** |
| 版（`APP_VERSION`） | 高 | なし | **付ける** |
| ブラウザ名・メジャー版・OS（UA の要約。生の UA 全文は送らない） | 中 | 低 | **付ける** |
| ウィンドウ幅×高さ・拡大率・PC／モバイル判定 | 高（拡大表示の不具合が多い＝Section 49・60） | なし | **付ける** |
| 表示部署（部署ID。名前は送らない） | 中 | 低 | **付ける** |
| 選択中のPJ／タスクの ID（名前は送らない） | 高 | 低（ID のみ。名前は管理者が ID から引く） | **付ける**（プレビューに「名前は送りません」と明記） |
| 並び順・まとめ方・フィルタの有無と種類（検索欄の文字列は除く） | 高 | 低 | **付ける** |
| 現在の経路（pathname と既知の `open` のみ。クエリ・ハッシュは除く＝招待コード対策） | 中 | 低 | **付ける** |
| 直近のクリック位置の座標（ビューポート比＋px） | 高 | なし | **付ける** |
| 直前の操作履歴（直近5件のクリック先：タグ名・role・`data-tour-id`・N秒前。文字・属性値なし） | 高（再現の主軸） | 低（メモリ上に保持し、送信時だけ送る） | **付ける**（キー入力は記録しない） |
| 直近のエラー（直近5分の fingerprint・code・回数。メッセージ本文は送らない） | 高（不具合のみ） | 低 | 段階2で付ける |
| DOM の構造（要素の種類だけ。深さ4・200ノード上限、文字・属性値なし） | 中（表示崩れの再現） | 低〜中 | 段階2・**既定オフ**（本人が任意でオン） |
| 画面の画像 | 中 | **高**（タスク名・顧客名・人名が写る）。取得ライブラリの導入は Section 19・外部ライブラリの扱いにも抵触 | **付けない**（構造データで代替） |
| タスク名・PJ名・コメントなど業務データ | — | 高 | **付けない**（本人が本文に書くのは自由） |
| メール・表示名 | — | 中 | スナップショットには**付けない**（送信者は RPC が member_id で決める） |

### 2.3 プレビュー

「送る内容を見る」で①人が読む1行ずつの要約（例：「画面：リスト／ブラウザ：Chrome 130／ウィンドウ 1280×720・拡大 125%／直前の操作：ボタン→行→…」）と、②実際に送る JSON を「コードで見る」でそのまま表示する（読み取り専用）。「画面の状況を付ける」をオフにすると、最小の項目（種類・コメント・画面名・版）だけを送る。
スナップショットは 16KB を上限とし、超えたら本文だけを保存する（本文を落とさない）。

## 3. 受ける側の体験

### 3.1 通知

通知レジストリ（`notificationKinds.ts`）に種類 `feedback`（audience＝super_admin、アプリ内は既定オン、Windows は未対応＝v1）を足す。Section 67 末尾の手順どおり、`in_app_notifications.kind` の CHECK 拡張・`ALL_IN_APP_KINDS`・`schemaChecks.ts`・i18n（ja・en）を同時に更新する。通知の作成は送信 RPC と同じトランザクション内で行い、受け手のチャネル設定は `kind_channels` の `#>` 判定（`::boolean` キャストを使わない＝Section 67 の指摘）で見る。クリック先は `/?open=admin-feedback`。

### 3.2 管理画面の一覧

設定の「アプリの管理」に新ページ `feedback`（カード「💬 ご意見・不具合」）を足す（`settingsPages.ts`・`resolveRequestedPage`・`/?open=` の対応を追加）。

- 一覧：受信日時・種類・本文の1行目・画面・版・状態・メモの有無。既定は「新規＋対応中」。状態と種類で絞り込み。
- 詳細：本文全文／スナップショットの人が読む表示と JSON／送信者名（管理画面のみ表示）。
- 状態：**新規／対応中／対応済み／見送り**。選択肢の切替は即時保存（途中状態が生まれない＝Section 65 の基準）。メモは保存ボタン方式（`useFormSave`）。

### 3.3 Claude にそのまま貼れる形でコピー

`errorCopyText.ts` と同じ考え方で純関数 `buildFeedbackCopyText` を作る。依頼文（再現手順の推定と改修案の相談）＋項目＋本文（コードブロック。柵は `fenceFor`）＋スナップショットを「人が読む形」と JSON の両方で出す。**送信者の ID・名前・メールは載せず**、コピー前に `redactSensitive` を再度通す。一覧では複数選択して1回でコピーできる。貼り先は Claude のみとする注意書きを付ける（本文には利用者の入力が含まれうる＝Section 67 のコピー欄と同じ）。

### 3.4 送った人への返信・対応状況

| 案 | 内容 | 評価 |
|---|---|---|
| 状況の見える化（送った内容タブに状態を表示） | 追加の通知なし | 段階1。低コストで「送りっぱなし」を避ける |
| `admin_messages` の再利用 | 1対1でお知らせを送る | 送達・既読・Windows を流用できる。ただし件との紐づけに列追加が要り、アプリ内が必ず届く（`inappLocked`）設計は「ご意見への返事」には過剰。意味も「指示」とずれる |
| 専用の状況通知（推奨） | 状態が「対応済み／見送り」に変わったとき本人へアプリ内通知。任意で一言（200字まで）を `reply_text` に保存し、送った内容タブにも表示 | 段階3。本人が設定でオフにできる種類 `feedback_status` として足す |

## 4. データ設計の骨子

### 4.1 テーブル `app_feedback`（マイグレーション1本・山本さんが手動適用）

| 列 | 内容 |
|---|---|
| id | 連番 |
| member_id | 送信者（`members.id` と同じ型【未確認：型は適用時に合わせる】） |
| group_id | 送信時の表示部署（論点2のため保存） |
| kind | `request`／`bug`／`other`／`unspecified`（CHECK） |
| comment | 1〜2,000字（CHECK。画面の上限は1,000字） |
| screen・route・app_version | 検索・集計用に列でも持つ |
| snapshot・snapshot_version | jsonb（nullable。構造は版管理） |
| status | `new`／`in_progress`／`done`／`wontfix`（CHECK。既定 new） |
| admin_memo・status_changed_at・status_changed_by | 管理者用 |
| reply_text | 段階3 |
| created_at・updated_at | 共有の `update_updated_at()` トリガー |

### 4.2 権限（書き込みはすべて RPC。表への INSERT／UPDATE／DELETE のポリシーは作らない）

- **表の SELECT は super_admin のみ**（`(SELECT current_member_is_super_admin())` で包む＝Section 39）。本人が自分の分を読む経路は RPC `list_my_feedback()`（id・日時・種類・本文・状態・reply_text だけを返す）。**行の RLS だけでは `admin_memo` を送信者から隠せないため、本人には表を直接読ませない。**
- `submit_feedback(...)`：SECURITY DEFINER・`SET search_path=''`・PUBLIC／anon から REVOKE。`current_member_id()` が NULL（匿名・未登録）なら例外。本人は引数でなく関数内で決める（他人を名乗れない）。
- `update_feedback_status(id, status, memo, reply)`：super_admin のみ（それ以外は例外）。
- `list_my_feedback()`：本人の行のみ。

### 4.3 乱用対策・伏せ字・保持

- 頻度上限：1人あたり1時間3件・1日10件。送信 RPC の冒頭でアドバイザリロックを取ってから件数を数える（Section 68 の独立レビューの教訓）。同一本文の1分以内の再送は throttled として黙って1件にまとめる。
- 伏せ字：本文とスナップショットの文字列は、画面側 `redactSensitive` と DB 側 `redact_client_error_text` の二重（メール・トークン類。Section 67）。スナップショットの構造は RPC が検証し、未知のキーは捨てる。
- 保持：**スナップショットは受信後90日で NULL にする**（`client_error_logs` と同じ。pg_cron・プレースホルダー無し）。行は、新規・対応中は消さず、対応済み・見送りは状態変更から180日で削除（「なぜ見送ったか」を残すため一般のログより長くする）。
- 版：`MIN_CLIENT_VERSION` は上げない（新規表と RPC の追加のみ。旧画面には入口が出ないだけ）。**適用順は SQL を dev→prod へ適用してから push**。未適用の間は管理ページに「適用がまだです」を出す（Section 24 Step Q の W2 と同じ方式）。

### 4.4 部署の管理者に自部署分を見せるか

論点2に集約。v1 は見せない。`group_id` を保存しておくため、後から RLS の1ポリシーを足すだけで拡張できる。

## 5. 段階リリース案と工数

実装は **設定画面リニューアルとリスト改善が終わった後**に着手する（`settingsPages.ts`・`SettingsView`・`ListView` を同時に触るため、並行すると衝突する）。

| 段階 | 利用者に見える変化 | 管理者に見える変化 | 工数 |
|---|---|---|---|
| 1 最小の往復 | ベルと設定「困ったとき」から、一言＋任意の種類で送れる。画面名・版・ブラウザ・ウィンドウ・拡大率・部署・選択ID・並び順・直近5件のクリック（座標と要素の種類）を自動で付け、プレビューで確認できる。「送った内容」タブで状態が見える | ベルに通知。設定に「ご意見・不具合」ページ（一覧・詳細・状態・メモ・Claude 用コピー） | **中（大寄り）**：表1・RPC3・通知の種類・モーダル・管理ページ・スナップショット構築・クリック履歴・コピー文面・テスト |
| 2 不具合の質を上げる | エラー表示の横の「この状況を報告」、ショートカット。DOM の構造を任意で付けられる | 直前のエラー（fingerprint）が紐づき、エラーページへ移れる | **小〜中** |
| 3 返事が返る | 対応済み／見送りの通知と一言の返信 | 返信欄。種類別・画面別の件数集計。（論点2で決めれば）部署管理者の閲覧 | **小** |

実装上の要点（developer 向けの骨子）：スナップショットの各項目は、`unsavedEditorRegistry` と同じ「画面側が getter を登録し、送信時に取りに行く」形（`snapshotContext.ts`）にして、MainLayout・リスト・ガント・カンバンの内部状態を直接読まない。クリック履歴は capture フェーズの1リスナーとメモリ上の5件だけで、`AuthenticatedApp` で起動しゲストでは起動しない。

## 6. 決めてほしい論点

1. **スナップショットの既定**：構造データだけを「既定オン＋送る前にプレビュー＋本人がオフにできる」とするか、既定オフ（本人が付ける）とするか。
   推奨：**既定オン**。10秒目標を守れるうえ、業務データを含まない許可リスト方式で、画像は付けない。プライバシーの懸念には、プレビューと「直近のクリックはこのブラウザのメモリにだけ保持し、送るときだけ送る」旨の1行の説明で応える。
2. **部署の管理者にも自部署分を見せるか**：
   推奨：**v1 は super_admin のみ**。要望の多くはアプリ全体の話で、見せると対応の責任が分散する。`group_id` は保存するので、段階3で部署固有の運用要望が多いと分かれば、自部署の分だけ見せるポリシーを足す。
3. **返信の方式**：
   推奨：**段階1は状況の表示のみ、通知と一言返信は段階3に専用の種類で足す**。`admin_messages` は再利用しない（3.4 の理由）。
4. **記名か匿名か**：
   推奨：**記名固定**（送信者は member_id で保存し、管理画面にのみ表示。Claude 用コピーには載せない）。数十名の組織では部署・画面・選択IDから特定でき、匿名ボタンは「匿名に見えるが特定される」という誤解を生む。気軽さは記入の少なさで担保する。
