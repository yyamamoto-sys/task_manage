# パスワード再設定の運用（Supabase 管理画面の設定とメール文面）

CLAUDE.md Section 79 の補足。**アプリ側の実装は v3.150 で完了しているが、Supabase 側の設定を済ませないと利用者にメールが届かない・リンクが開けない。**
ファイル名に「password」を含めていないのは、開発環境の Read/Write 拒否ルール（`*password*`）に当たるため。

事実は Supabase の公式ドキュメント（2026-10-14 に参照）で確かめた。確かめられなかった点は「未確認」と書いた。

## 1. 管理画面でやること（本番・dev それぞれ）

### 1-1. URL の設定（Authentication → URL Configuration）

| 項目 | 入れる値 | 根拠 |
|---|---|---|
| Site URL | 本番のアプリのアドレス（Vercel の本番 URL） | 公式：`redirectTo` を指定しなかった場合の既定の戻り先。パスワード再設定のメールにも関わる。既定値は `http://localhost:3000` なので本番の URL に変える |
| Redirect URLs | 本番のアドレス（例 `https://<本番ドメイン>/`）と、ローカル開発の `http://localhost:5173/`（Vite の既定ポート。`http://localhost:5173/**` でもよい） | 公式：戻り先（`redirectTo`）は許可リストに載せておく。ワイルドカード `*` は `.` と `/` を含まない文字列、`**` は `/` を含む任意の文字列に一致する。本番は正確なパスで書き、`**` はローカル開発・プレビュー向け |

- このアプリは `resetPasswordForEmail(email, { redirectTo })` の `redirectTo` に **「アプリのアドレス（origin ＋ pathname）」だけ**を渡す（クエリ・ハッシュは付けない）。本番なら `https://<本番ドメイン>/`、ローカルなら `http://localhost:5173/`。許可リストにこの形が一致していること。
- 管理画面のメニュー名（Authentication → URL Configuration）は、公式ドキュメントが「URL Configuration のページ」と書いている範囲の確認。ダッシュボードの実際の表示は **未確認**（画面で確かめる）。
- 許可リストにない `redirectTo` を渡したときの挙動は、公式ドキュメントに記載がなく **未確認**。「リンクを開いたら Site URL に飛ぶ」などになりうるので、必ず上の2件を入れてから試す。
- Vercel のプレビュー（ブランチ）で試す場合は `https://*-<チーム名>.vercel.app/**` 形式を許可リストに足す（公式の推奨例）。

### 1-2. メール送信（Authentication → Emails → SMTP）

| 事実 | 内容 | 根拠 |
|---|---|---|
| 標準の送信（組み込み）の宛先 | **そのプロジェクトのチーム（組織のメンバー）宛てにしか送れない。** それ以外の宛先は「Email address not authorized」で失敗する | 公式：Custom SMTP のページ |
| 標準の送信の数 | **1時間に2通まで**（予告なく変わりうる）。ベストエフォートで、到達・稼働の保証（SLA）は無い | 公式：Custom SMTP・Rate Limits のページ |
| 利用者に届けるには | **社用の SMTP を設定する**（SMTP のホスト・ポート・ユーザー・パスワードを控えて、管理画面で Custom SMTP を有効にして入力する） | 公式：Custom SMTP のページ |
| SMTP 設定後の既定の上限 | **1時間に30通**（変更は Authentication → Rate Limits） | 公式：Custom SMTP のページ。Rate Limits のページには「Custom SMTP では上限を変えられる」とある |
| 同じ人への再設定メール | **1ユーザーあたり60秒に1回**が既定（プロジェクトで変更可）。超えると HTTP 429 | 公式：Rate Limits のページ（`/auth/v1/recover` と `/auth/v1/otp`）。エラーコードの名前（`over_email_send_rate_limit` 等）は公式ページに **記載なし（未確認）**。アプリは HTTP 429 とメッセージの内容の両方で判定している |

確認手順（メールを実際に届ける前に）：

1. 管理画面で「Authentication → Emails → SMTP」を開き、Custom SMTP が **有効**になっているかを見る（メニュー名は公式が `/auth/smtp` と書いているページ。ダッシュボードの実際の表示は **未確認**）。
2. 無効のままなら、チーム外のメールアドレス（利用者のほとんど）には再設定メールが届かない。社用 SMTP の情報（情報システム部門に確認）を入れて有効にする。
3. 設定後、自分とチーム外のアドレスの両方で「パスワードをお忘れの方」を試し、迷惑メールに入っていないか・差出人名が想定どおりかを確認する。
4. 1時間あたりの上限（既定30通）が、全員が一斉に再設定したときに足りるかを見積もる（Rate Limits で変更できる）。

### 1-3. 戻りリンクの有効期限

- 公式の Rate Limits／Email OTP のページと CLI の設定リファレンスに、メールの OTP の有効期限は **既定 3600 秒（1時間）**（`auth.email.otp_expiry`）とある。再設定リンクもこの設定に従うかは、公式ドキュメントに明記がなく **未確認**。
- 管理画面でこの設定がどこにあるか（画面上の名前）も **未確認**。
- メール文面の「有効期限」は、確認できるまで「短い時間で無効になります」と書く（下記の案はそうしている）。確認できたら「送信から1時間」等に直す。

### 1-4. 「現在のパスワードの確認（Secure password change）」の設定

- 公式（検索結果の要約から確認。原文は **未確認**）：Supabase には、パスワード変更の前に再認証を要求する設定「Secure password change」（メールプロバイダーの設定にある）がある。オンのとき、ログインから時間が経ったセッション（目安は24時間より前）でパスワードを変えるには、`reauthenticate()` で届くワンタイムの値が要る。
- **このアプリの設定ページ「パスワードを変更」は再認証の入力欄を持たない。** この設定がオンの本番では、ログインから時間が経った人が変更しようとするとエラーになる（アプリはそのエラー文を表示し、「一度ログアウトして『パスワードをお忘れの方』から再設定」を案内する）。
- 実際に本番でこの設定がオンかどうかは、管理画面で **要確認**（オフなら、設定ページから常に変更できる）。オンのままにする場合の運用は上の案内で足りる。再認証の入力欄を設定ページに足すかは、運用が始まってから判断する。
- `updateUser` に `current_password` を渡せば、現在のパスワードの確認ができる（公式：Password-based Auth のページ。supabase-js v2.102.0 以上）。このアプリは使っていない。

## 2. 「Reset Password」メールのテンプレート（管理画面に貼る文面案）

場所：Authentication → Emails → Templates →「Reset password」（公式のテンプレート一覧の名前。ダッシュボード上の並びは **未確認**）。

使える変数（公式）：`{{ .ConfirmationURL }}`（リンク）・`{{ .SiteURL }}`・`{{ .RedirectTo }}`・`{{ .Email }}`・`{{ .Token }}`・`{{ .TokenHash }}`・`{{ .Data }}`。

### 件名

```
【AMP（アミタ業務管理）】パスワード再設定のご案内
```

### 本文（HTML）

```html
<p>AMP（アミタ業務管理）をご利用いただきありがとうございます。</p>
<p>パスワードの再設定を受け付けました。下のリンクを開き、新しいパスワードを設定してください。</p>
<p><a href="{{ .ConfirmationURL }}">パスワードを再設定する</a></p>
<p>このリンクは一度しか使えず、短い時間で無効になります。期限が切れた場合は、AMP のログイン画面の「パスワードをお忘れの方はこちら」から、もう一度メールを送ってください。</p>
<p>リンクを開いても「無効か期限切れ」と表示される場合は、お使いのメールのセキュリティ機能がリンクを先に開いてしまっている可能性があります。もう一度メールを送り、届いたらすぐにリンクを開いてください。</p>
<p>このメールに心当たりがない場合は、何もせずにこのメールを破棄してください。パスワードは変更されません。</p>
<p>※このメールは送信専用です。返信はできません。</p>
<p>AMP（アミタ業務管理）</p>
```

- 「先に開いてしまう」の一文の根拠：公式のメールテンプレートのページに「メールプロバイダーによってはスパム検出などでメール内の URL を先読みし、`{{ .ConfirmationURL }}` が使用済みになって "Token has expired or is invalid" になる」とある。
- 有効期限の時間は、1-3 のとおり未確認のため書いていない（確認できたら「送信から◯時間」を足す）。
- 差出人の名前・アドレスは SMTP の設定（Sender email / Sender name）で決まる。「AMP（アミタ業務管理）」にそろえる。
- 「Password changed」（パスワードが変更されたことの通知メール）のテンプレートが公式の一覧にある（Security notification の1つ）。使うかどうか、既定でオンかオフかは **未確認**。使うなら、誤って変更された場合の連絡先（管理者）を書く。

## 3. 動作確認の手順（山本さん・実機）

1. 管理画面の 1-1・1-2 を設定する。
2. ログイン画面で「パスワードをお忘れの方はこちら」→ 自分のメールを入れて送信 → 「入力したメールアドレスが登録されていれば…」が出ること。**登録していないメールアドレスでも、まったく同じ文言が出る**こと。
3. メールのリンクを開く → 「新しいパスワードを設定」だけが出る（アプリの通常画面が出ない）→ 6文字以上を2回入れて設定 → 「パスワードを変更しました」でそのままアプリに入れること。
4. 古い・使用済みのリンクを開く → 「このリンクは無効か期限切れです。パスワードの再設定の場合は…」と出て、ログイン画面の再設定フォームが開くこと。
5. **再設定リンクを開いて「新しいパスワードを設定」が出た状態で、再読み込み・新しいタブでアプリのアドレスを開く** → やはり「新しいパスワードを設定」が出て、通常のアプリへ入れないこと（「設定せずにログイン画面へ戻る」を押すとログイン画面になり、その後は再読み込みしても再設定画面は出ない）。
6. **URL の履歴にトークンが残らない**こと：リンクを開いたあと、アドレスバーに `#access_token=…` が無く、ブラウザの「戻る」を押してもトークン付きの URL に戻らない（履歴を右クリックして一覧を見る）。
7. **既存のフローが壊れていない**こと（`detectSessionInUrl` を切ったため、全メールリンクを自前で取り込んでいる）：
   - サインアップ確認：新規登録 →（メール確認が有効な環境で）確認メールのリンクを開く → そのままログイン状態でアプリ（またはメンバー未登録の案内）に入ること。「再設定」の画面は出ないこと。
   - 招待コードでの登録：招待リンク（`?invite=…`）から登録 → 確認メールのリンク → 参加が完了すること（Section 25 Phase 3）。
   - 古い確認メールのリンクを開く → 汎用の「リンクが無効か期限切れです」が出ること（「再設定」とは言わない）。
   - すでにログインしている状態で、古い再設定リンクを開く → アプリにそのまま入り、トースト「リンクが無効か期限切れです」が出ること。
8. 設定ページ「プロフィール」→「パスワードを変更」から変更できること（Secure password change がオンなら、ログインから時間が経っているとエラー文と案内が出ること。今と同じパスワードを入れると「今と同じパスワードは使えません」が出ること）。
5. 設定ページ「プロフィール」→「パスワードを変更」から変更できること（Secure password change がオンなら、ログインから時間が経っているとエラー文と案内が出ること）。

## 3-2. なぜ `detectSessionInUrl` を切ったか（実装メモ）

- supabase-js（auth-js）は既定でハッシュのトークンを自動処理し、その後 `location.hash = ''` で消す。**この代入は履歴に新しい項目を積む**（`history.replaceState` ではない）ため、アプリ側で後から `replaceState` しても、戻るボタンでトークン付きの URL が復元できてしまう。
- そこで `createClient` に `auth: { detectSessionInUrl: false }`（`flowType` は既定の implicit のまま）を指定し、ハッシュの処理を自前にした：起動時に URL を控えて**直ちに `replaceState`** で消し、`setSession({ access_token, refresh_token })` で取り込む。
- 影響範囲：再設定だけでなく、サインアップ確認・招待・マジックリンク・メール変更のリンクも同じ経路（トークンが揃っていれば type を問わず取り込む）。`type=recovery` のときだけ再設定画面を出す。
- 再設定画面の途中で再読み込み・新しいタブを開いても通常のアプリへ入れないよう、localStorage に「再設定待ち」の印（`recovery_pending_v1`。ユーザー ID・時刻のみでトークンは含まない）を残す。パスワードの設定・ログイン画面へ戻るで消える。24時間を超えた印・セッションと一致しない印は無効（消す）。localStorage が使えない環境では印を書けず、再読み込みすると通常起動になる（既知の限界）。
