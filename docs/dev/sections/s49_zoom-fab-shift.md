## 49. 拡大率・フォント設定でFAB/保存ボタンがズレる問題への対応（必須・v3.94・2026-08-21）

### 何が起きていたか

v3.91/v3.92で右下スタック（Section 43）を一元管理する`bottomStack.ts`を作ったが、土台の値（`SIDE_PANEL_FOOTER_HEIGHT_PX`等）は「padding・ボタンサイズからの計算による見積もり」のままだった。ブラウザの拡大率・最小フォントサイズ設定・OSの表示スケール・フォント差異により実際の描画サイズが変わりうるため、「人によっては＋ボタンと保存ボタンが依然として被る」というクレームが（v3.91の対応後も）再発した。値を微調整して回避しても、別の拡大率・フォント設定の利用者でまた同じ問題が起きる（見積もりである限り再発し続ける）と判断し、今回は見積もり依存そのものを減らす方向で対応した。

### 2-1（本命）：FABをTaskSidePanelの横へ退避させる

`TaskSidePanel`の開閉状態と実際の幅（`panelWidth`。ドラッグでユーザーが変更できる値）を、新設した`src/stores/uiLayoutStore.ts`（zustand）で共有した。`TaskSidePanel`はマウント時に`isTaskSidePanelOpen=true`、アンマウント時に`false`をセットし、`panelWidth`が変わるたびに`taskSidePanelWidth`を更新する。`MainLayout.tsx`はこのストアを購読し、`QuickAddFab`へ新設した`extraAvoidWidthPx`（TaskSidePanelが開いていればその幅、閉じていれば0）propとして渡す。`QuickAddFab`は既存のAI相談パネル回避ロジック（`isConsultOpen ? consultPanelWidth : 0`）に、この`extraAvoidWidthPx`を単純加算する。

- **両方が同時に開く場合の扱い**：加算する。AI相談パネルとTaskSidePanelは画面右側に横並びで両方同時に開きうる（`MainLayout.tsx`の描画順は [mainContent（TaskSidePanelを含む）][AI相談パネル]）ため、両方の幅を避けなければ衝突が起きる。
- **`TaskSidePanel`はPC・タブレット専用でモバイルには出ない**（Section 43既出の前提のまま）ため、モバイル向けFABには`extraAvoidWidthPx`を渡していない（影響なし）。

**縦位置（v3.91で52pxへ上げていたもの）は24pxへ戻した。** 理由：横方向でFABが完全にTaskSidePanelの外へ出るため、フッターとの縦の衝突は構造的に起きなくなった（衝突は「同じ横位置にいるときだけ」発生するため）。「少し上へずらす」指示（v3.91）はフッターとの衝突を避けるための手段であり、衝突が構造的に起きなくなった以上、目的は既に達成されている。これに伴い`FAB_BOTTOM_PC_PX`を`SIDE_PANEL_FOOTER_HEIGHT_PX + STACK_CLEARANCE_PX`（52px）から、v3.86以前と同じ`24px`の固定値に戻した（ショートカットボタン・Toastのbottomもこの値からの積算のため連動して下がり、v3.90時点の値＝84pxに一致する）。

これに伴い、`sidePanelFooter`（TaskSidePanelフッター）は`bottomStack.ts`の1次元（縦方向のみ）の重なりモデルから外した。`bottomStack.test.ts`はbottom座標と高さだけを見る1次元の検査であり、「横に退避しているから実際には重ならない」という2次元の関係を表現できない（footerとfabが同じ横位置にいる前提が崩れたため、この2要素間の「重ならないこと」はこのテストの対象外とし、後述のランタイム実測チェック（2-3）に委ねる）。

### 2-2：残る関係（FAB↔ショートカット↔Toast↔ボトムナビ）は(c)を選んだ

これらは既に「高さの見積もり値を、対応するコンポーネント自身の明示`height`としても使う」設計（v3.91）になっており、FAB(48px固定の円)・ショートカットボタン・Toast本体はいずれも`bottomStack.ts`の定数をそのまま`style.height`に使っている＝見積もりと実体は既に同じ値を参照している。

(a)（ResizeObserver実測）を検討したが、以下の理由で見送った：
- これらの高さは既に固定`height`のCSSボックスであり、ResizeObserverで測っても`bottomStack.ts`の定数と同じ値が返るだけで、実質的な追加情報が無い。
- 拡大率・最小フォントサイズで実際に起きうる問題は「固定`height`のボックスから、内部のテキスト/ボタンが`overflow`しはみ出す」ことであり、これは親要素のボックス自体のサイズ（ResizeObserverが測るもの）ではなく、はみ出した子要素の描画位置に起因する。ResizeObserverは検知できない種類のズレのため、(a)は今回の問題を解決しない。
- `Toast`は`App.tsx`直下、`FAB`/`ショートカット`は`MainLayout.tsx`と、コンポーネント境界をまたぐ実測の受け渡し（測る側→使う側の反応的な状態共有）が必要になり、実装コストの割に上記の理由で効果が薄い。

(b)（1つのfixedなflexコンテナ+gap）も検討したが、Toast(z10000)・ショートカット(z140)・FAB(z60)はモーダル/フォーカスの重なり順の都合で意図的にz-indexが分かれており、同じコンテナにまとめるとこの重なり順の意図を壊すリスクがあるため見送った。

よって**(c)**：明示`height`による最小保証は維持しつつ、`STACK_CLEARANCE_PX`を12px→16pxへ引き上げた。ただしこれは「見積もりを少し大きくする」だけであり、今回のクレームの構造（値を足しても別の設定でまた起きる）そのものへの解決にはならないと認識している。この関係性における実質的な再発防止策は、次の2-3のランタイム実測チェックに委ねる。

### 2-3：開発ビルド限定のランタイム重なり検出（今回の再発防止の本体）

`src/lib/layout/devOverlapCheck.ts`を新設した。`TaskSidePanel`フッター・FAB本体・ショートカットボタン・Toast・モバイルのボトムナビに`data-bottom-stack="..."`属性を付与し、開発ビルド（`import.meta.env.DEV`）でのみ、`MainLayout`のマウント時に0.5秒間隔で各要素の`getBoundingClientRect()`を取得し、`bottomStack.test.ts`と同じ`ALLOWED_OVERLAPS`（Toast×ショートカット・Toast×FABメニュー）を除く組み合わせが実際に画面上で重なっていたら、要素名・重なり幅（px）を`console.warn`に出す。

**山本さんが気づく方法**：開発サーバー（`npm run dev`）で画面を開き、ブラウザの拡大率やOSの文字サイズ設定を変えながらタスク詳細を開閉する。実際に重なりが起きた瞬間、DevToolsのコンソールに`[bottomStack] 実測で重なりを検出: "fab" × "toast"（約12×8px）`のような警告が出る。本番ビルドでは`import.meta.env.DEV`が`false`になるため何も実行されず、利用者には見えない。

### CLAUDE.md新設ルール：右下スタックの土台に描画サイズの見積もり値をハードコードしない

`bottomStack.ts`の値は**v3.91→v3.94の2回、同じ「見積もりと実物のズレ」ですり抜けた**（1回目：v3.86のFAB位置固定値がフッターと衝突／2回目：v3.91で「少し上へ」対応した後も、拡大率・フォント設定次第でなお衝突しうるクレームが再発）。理由は、ブラウザの拡大率・最小フォントサイズ設定・OSの表示スケール・フォントの行高差により、CSSで指定した`height`と実際に描画される見た目上のサイズが一致しない利用者が一定数いるため。**値を足して回避する対応（v3.91の「28px上げる」）は、対応した瞬間の環境でしか正しさを保証できず、別の環境の利用者で必ず再発する。**

今後、右下（PC）・画面下端（モバイル）に新しい要素を積む・既存の関係を調整するときは：
- まず「本当に見積もりが要るか」を疑い、**位置関係そのものを構造的に無くせないか**（今回のFABの水平退避のように）を最優先で検討する。
- 見積もりに頼らざるを得ない場合は、`bottomStack.test.ts`のような定数どうしの整合性テストだけでは「見積もりが実物と合っているか」を検査できないことを踏まえ、`devOverlapCheck.ts`のような実測ベースの検査を併設する。
- クリアランスを増やすだけの対応は暫定策であり、恒久対応として報告しないこと。
