## 44. グランドルール：タスク編集面（モーダル／サイドパネル）は明示保存にする（必須・v3.87・2026-08-20）

クレーム「タスクの詳細を追加した後、自動で保存されて×で消すの、本当に反映できてるか分からなくて不安。自動保存されているかどうかに関わらず、自分で保存ボタンを押したら画面が閉じるという流れの方が安心できる」への対応。

### 何を変えたか

`TaskEditModal.tsx`（タスク編集モーダル）・`TaskSidePanel.tsx`（右サイドパネル）の**`form`／`sidebarForm`（このタスク自身のフィールド）は、以後 保存ボタン／Enter／Ctrl(Cmd)+Enter でのみ保存する**。以前は`form`変更を600msデバウンスして自動保存し、×やタスク切替時に保留分をその場でフラッシュする設計だった（編集消失バグへの対処としてコメント付きで入っていた）が、この自動保存の仕組み自体が「保存されたか分からず不安」というクレームの原因のため、丸ごと廃止した。

- **保存ボタンは常時表示**。押すと保存して閉じる（モーダル）／押しても閉じない（サイドパネル。元々✕でしか閉じない設計）。dirty（保存済み内容と差分がある）でなければ`disabled`＋明度を下げ、`title`で「変更はありません」と伝える。dirty判定は`src/lib/taskEditPayload.ts`の`computeFormDirty()`（値の比較。担当者・タグは順序を無視した集合比較）。
- **Enterで保存できるが、画面は閉じない**。単一行の`<input>`（タスク名等）でのEnterのみ対象。`<textarea>`（メモ・コメント）のEnterは改行のまま。**Ctrl(Cmd)+Enterはどこからでも保存**（captureフェーズで拾い、タグ入力欄・CustomSelectの検索inputが先にpreventDefaultしていても必ず発火する）。日本語入力の変換確定のEnter（`e.nativeEvent.isComposing`）は必ず無視する。
- **保存済み（未変更）のときは保存ボタンをdisabled＋明度を下げる**。既存の`SaveIndicator`（✓保存しました／保存失敗のバッジ）とは役割を分離した：保存ボタン＝「押せるか・保存中か」、`SaveIndicator`＝「結果（成功／失敗）」の伝達のみに専念する（両方が別々に「保存中」を語らないようにするため、`SaveIndicator`はidle/savingのとき何も表示しない）。

### なぜ自動保存をやめたか

自動保存自体が悪いわけではなく、**「今どういう状態なのか利用者から見えない」**ことが不安の原因だった（保存済みかどうかの手がかりが薄いSaveIndicatorだけでは足りなかった）。明示保存にすると「押した／押していない」「押せる（変更あり）／押せない（変更なし）」が常に視覚的に分かるため、同じ不安を構造的に無くせると判断した。

### なぜjoin系（タスクフォース・追加プロジェクト・先行タスク・子タスクの付け外し）だけは即時のままか

これらは`form`を経由しない別テーブルへのadd/remove操作（`addTaskTaskForce`/`removeTaskTaskForce`・`addTaskProject`/`removeTaskProject`・`addTaskDependency`/`removeTaskDependency`・`TaskSidePanel`の`applyChildren`/`detachChild`）で、**操作した瞬間に結果（チップの増減）が画面に見える**。これらまで保存ボタンの対象にすると「チップは増えたのに保存ボタンを押すまで本当に登録されたか分からない」という、今回解消したかった不安の別形態を新たに生む。この線引きは両ファイルの冒頭コメント・各セクションのインラインコメントに明記した。

### close時の暗黙フラッシュは廃止した

以前は×ボタン・タスク切替のたびに、保留中の編集をその場で`saveTask`する「フラッシュ」処理があった（デバウンス発火前のアンマウントで編集が消える実データロスバグへの対処としてコメント付きで入っていた）。明示保存に変えた今、このフラッシュを残すと「保存ボタンを押していないのに閉じたら保存された」という、今回のクレームの裏返しが起きるため削除した。代わりに、閉じる・タスクを切り替える経路すべてでdirtyなら`confirmDialog()`により確認する：

- **×ボタン・オーバーレイクリック（モーダルのみ。サイドパネルはSection 21の対象外でクリックアウトサイド自体が無い）**：「保存していない変更があります。破棄して閉じますか？」／選択肢「破棄して閉じる」「編集に戻る」の2択。**3択（保存して閉じる、を含む）にはしなかった**：保存したいだけなら常時表示の保存ボタンが既にあるため、確認ダイアログ側にまで持たせる必要は薄いと判断した（実装・文言とも複雑になる）。
- **サイドパネルのタスク切替**：他の行をクリックして別タスクを選ぶと、旧タスクにdirtyな変更があれば「「◯◯」に保存していない変更があります。破棄して次のタスクへ移動しますか？」／選択肢「破棄して移動する」（confirm・tone="danger"）「保存してから移動する」（cancel）の2択で確認する。**「切り替えをキャンセルして元のタスクに留まる」（＝呼び出し元の選択そのものを差し戻す確認）は実装していない**：3つの呼び出し元（`GanttView`/`KanbanView`/`ListView`）がそれぞれ独自に選択中タスクIDを持っており、「切り替えを取り消す」には呼び出し元へ選択を戻す新しいコールバックが要る。「切り替え自体は進む前提で、保存するか破棄するかだけを聞く」の2択で「黙って破棄しない・黙って保存しない」という要件は満たせるため、3ファイルへの越境変更は見送った（ただし保存が実際に失敗した場合の選択の巻き戻しはv3.88で対応。Section 45参照）。**confirm=破棄・cancel=保存という割り当て（v3.88）**：`ConfirmModal`は背景クリックで必ず`cancel`（false）扱いになるため、うっかり背景をクリックしても編集内容が保存される側に倒れるよう、「破棄」をtone="danger"のconfirmボタン（赤・押すのに意図が要る）に、「保存」を安全側のデフォルト（cancel・背景クリック）に割り当てている。
- **Escキー**：現状どちらの画面にもEscapeで閉じる機能自体が実装されていない（調査済み）。今回は新しい閉じる経路を追加していないため対応不要（存在しない機能に警告を追加する必要は無い）。

### finalized_mentions（@メンション通知）の扱い

以前は「閉じた時だけ確定保存する」という別仕様だった（`TaskEditModal.tsx`のみ・サイドパネルは元々メンション機能自体が無い）。明示保存に変えたことで「閉じるまで通知が飛ばない」という仕様の前提（close時フラッシュ）が消えたため、**保存のたびに常に`finalized_mentions`をペイロードへ含める**形に寄せた（`extractMentions(form.comment)`を毎回計算）。変化が無ければ同じ値を書き込むだけで実害は無く、「変更があったときだけ」という条件分岐（旧`mentionsEqual`比較）自体が不要になった。

### 2-5：競合の窓が広がる問題への対策（`saveTask`自体には手を入れない）

明示保存でフォームを開いたままの時間が延びると、Realtimeで他人の更新が届いても`saveTask`内部の`expectedUpdatedAt`（store の現在値から読む）がその新しい値に更新済みになり、競合が検知されないまま自分の内容で上書きしてしまう抜け穴が広がる（Section 5参照）。**`saveTask`の共通ロジック・Section 5の契約は一切変更していない。** 代わりに両画面それぞれの中で：

- フォームを開いた時点／保存に成功した時点の`updated_at`を`baselineUpdatedAtRef`に保持する。
- 保存直前に、その時点で分かっている`updated_at`（storeから購読済みの値）と`baselineUpdatedAtRef`を比較し、異なれば「このタスクは他の人が更新しました。あなたの内容で上書きしますか？」を`confirmDialog()`で確認してから保存する（拒否したら保存しない）。
- 開いている最中に他人の更新が届いたことは、控えめな警告バナー（⚠ 他のメンバーがこのタスクを更新しました…）で画面上にも知らせる。

### 機械チェック

`src/components/task/__tests__/explicitSaveNoDebounce.test.ts`が、`TaskEditModal.tsx`/`TaskSidePanel.tsx`に`form`/`sidebarForm`を依存配列に持つ`useEffect`が`setTimeout`と組み合わさっている（＝デバウンス自動保存の実装フィンガープリント）ことを検出するテスト。実装前にv3.86時点（デバウンスが実在した状態）のソースに対して実際に走らせ、正しく検出できる（＝赤くなる）ことを確認済み。検出ロジック自体が壊れていないことを合成フィクスチャでも固定している。
