# プロジェクト招待（部署外メンバーの受け入れ）設計

作成：2026-08-10（統括Claude／山本さんとの設計セッション）
発端：メンバーからの依頼「その部署に所属していない人たちを、特定のプロジェクトに招待したい」。部署をすべて登録しきっていないため、これまでアプリを使ったことがない人に1つのPJへのアクセスを渡す必要がある。

関連：`CLAUDE.md` Section 1.6（マルチテナンシー・RLS・**過去に実際に起きた事故と教訓**）／Section 4（物理削除禁止）／Section 15（エラー表示）／Section 21（モーダル契約）

---

## 0. 一行

**新しいアクセス制御の軸を作らない。「招待用の部署」を1つ作り、既存の複数部署アクセス機構（`group_ids` 配列）に乗せる。RLSは1行も変えない。**

---

## 1. 実測した前提

- アクセス制御は**部署単位のみ**。全テーブルのRLSが `group_ids && current_member_group_ids() OR current_member_is_super_admin()`
- **プロジェクト単位のアクセス制御の土台は存在しない**。設計上の `ProjectMember`（PJ×メンバーの多対多）は **DBに作られていない**
- 認証は **Supabase Auth のメール＋パスワード**（`signUp` / `signIn`）。マジックリンクは未使用
- `guard_member_privilege_columns` トリガーにより、**部署の作成と `group_ids` の直接付与は全社スーパー管理者に限定**されている（権限昇格ガード）
- 未登録の認証ユーザーには `AccessDeniedScreen` が出る。真の初回だけ `bootstrap_first_group_and_member()`（SECURITY DEFINER）で抜ける経路がある＝**SECURITY DEFINER 関数で members を作る先例がある**

## 2. 山本さんの決定（2026-08-10）

| 論点 | 決定 |
|---|---|
| 招待先 | **社内の別部署**（社外ではない） |
| 見せる範囲 | PJとタスク／担当する社内メンバーの氏名／タスクの編集権限／AI機能／**そのPJに関連する機能のすべて**。「アプリを認知してもらう機会」でもあるので、弊害が無い範囲で他の機能も見せる |
| 実装方式 | **案A：招待用の部署**（RLSを変えない） |
| 発行権限 | **全メンバーが発行可** |
| 将来 | 本人の本当の部署が登録されたら**ホーム部署を付け替える** |

## 3. 🔴 ご提案から変更した点（重要）

当初案「**プロジェクトコードとメールアドレスを入力すればサインインできる**」は**採用しない**。

理由：プロジェクトコードもメールアドレスも秘密として扱えない情報であり、コードが1度転送されればそのアドレスを知る誰でも入れる。しかもアプリ全体で最も弱い認証経路になり、社内データ全体のリスクがそこに集中する。

代わりに：**認証は既存のメール＋パスワードに乗せる。招待コードは「どのPJ・どの部署に紐づけるか」を決めるためだけに使う。** そのうえで当初案 2(b)（発行時に相手のメールを入力する）を、記録ではなく**検証条件**として使う。

## 4. 設計

### 4-1. 招待用部署

- **PJごとに1つ**作る（1つを使い回すと別PJの招待者に他PJが見えてしまう）
- `groups` に `is_invite_group boolean NOT NULL DEFAULT false` を追加し、管理画面で通常部署と区別する
- 対象PJの `projects.group_ids` に招待用部署を追加する
- 招待者は `members.group_id` ＝招待用部署、`is_admin=false` / `is_super_admin=false`

### 4-2. 担当者の氏名を見せるための兼務

招待用部署に入れただけでは、招待者から**社内メンバーが見えない**（`members` も部署スコープのため担当者欄が「未担当」になる）。

→ **招待を発行した本人**と **`projects.owner_member_id`** に、招待用部署を `group_ids` の兼務として自動付与する。それ以外の社内担当者は管理画面から手動で追加する。

副作用：兼務した社内メンバーのサイドバーに「表示部署」の切替が出る（アクセス可能な部署が2件以上のときに表示される既存仕様）。実害なし。

### 4-3. 招待の検証（4条件すべてを満たすときだけ登録できる）

1. コードが存在し、**未使用**（`accepted_at IS NULL`）かつ**未取消**（`revoked_at IS NULL`）
2. **発行から24時間以内**
3. **入力されたメールアドレスが、招待時に指定されたアドレスと完全一致**、かつ **`auth.email()` とも一致**（なりすまし防止。`bootstrap_first_group_and_member()` が `auth.email()` を使う先例に倣う）
4. コードは推測不能な長さのランダム値。**DBにはハッシュで保存**する（平文で持たない）

3が要。**コードが転送されても、招待された本人以外は登録できない。**

### 4-4. 「全メンバー発行可」に対する安全弁

発行権限を全員に開くため、代償として次を必ず入れる。

- 🔴 **自分がアクセスできる部署のPJしか招待できない。** SECURITY DEFINER 関数はRLSを迂回するため、関数の中で「呼び出し者の `current_member_group_ids()` と対象PJの `group_ids` が重なるか」を**明示的に検証**する。これが無いと、任意のPJへのアクセスを誰でも配れる
- 🔴 **招待先メールアドレスのドメイン許可リスト。** 社内限定の運用なので、許可ドメイン以外への招待を弾く。設定可能にする（社内に複数ドメインがありうるため）。**社外への誤招待を構造的に防ぐ最も効く安全弁**
- **監査**：誰が・誰を・どのPJに・いつ招待し、いつ使われたかを記録する。管理画面に招待一覧を出し、**取り消し**できるようにする
- 招待で配れるのは**そのPJ1件のみ**（部署全体のアクセスは配れない）

### 4-5. 招待された人に見えるもの

招待用部署のデータ＝**そのPJだけ**が見える。その状態で機能はフルに使える。

| | |
|---|---|
| ダッシュボード・カンバン・ガント・リスト・ワークロード | 使える（データはそのPJのぶんだけ） |
| マイページ・カレンダー・体制図・関係性グラフ | 使える |
| タスクの作成・編集 | できる |
| AI相談・PJ分析 | 使える（PJデータがAnthropicへ送られ、コストも発生する） |
| 設定画面 | 一般メンバーのため編集不可 |
| OKRモード | 招待用部署にOKRが無いため空。個人OKRは本人のみなので使える |

### 4-6. 将来の本格導入への移行

登録時に**実ユーザーと同じ情報（メールアドレス・氏名）を取得**する（当初案 1(c) のとおり）。本人の本当の部署が登録されたら、`members.group_id`（ホーム部署）を付け替え、招待用部署は `group_ids` の兼務として残すか外す。**アカウントを作り直さない。**

## 5. データモデル

### `project_invites`（新規）

| 列 | 型 | 備考 |
|---|---|---|
| `id` | uuid PK | |
| `project_id` | text NOT NULL | 対象PJ |
| `invite_group_id` | text NOT NULL | 招待用部署 |

| `code_hash` | text NOT NULL | **平文を保存しない** |
| `invited_by` | text NOT NULL | 発行者（監査） |
| `expires_at` | timestamptz NOT NULL | 発行＋24時間 |
| `accepted_at` / `accepted_member_id` | | 使用済みの記録 |
| `revoked_at` / `revoked_by` | | 取り消し |
| `created_at` | timestamptz | |

RLS：発行者と同じ部署のメンバーが参照できる（監査のため）。`code_hash` はクライアントに返さない。

### `groups` への追加

`is_invite_group boolean NOT NULL DEFAULT false`

## 6. SECURITY DEFINER 関数（3本）

- **`create_project_invite(p_project_id, p_email)`**
  1. 呼び出し者が対象PJにアクセスできるか検証（4-4の1点目）
  2. メールドメインの許可リスト検証
  3. 招待用部署が無ければ作成し、PJの `group_ids` に追加
  4. 発行者と `owner_member_id` に招待用部署を兼務付与
  5. コードを生成して**ハッシュで保存**し、平文は戻り値で1度だけ返す

- **`accept_project_invite(p_code, p_email, p_display_name, ...)`**
  1. 4-3の4条件を検証
  2. `members` 行を作成（招待用部署所属・管理者フラグは必ず false）
  3. `accepted_at` / `accepted_member_id` を記録

- **`revoke_project_invite(p_invite_id)`**（Phase 2で追加。`migrations/20260810b_add_revoke_project_invite.sql`）
  1. 呼び出し者が `current_member_id()` を持つことを検証
  2. 呼び出し者が対象招待の `project_id` のPJにアクセスできることを `can_access_group_ids` で検証（`create_project_invite()` と同じ考え方。これが無いと他部署の招待を取り消せてしまう）
  3. 既に `accepted_at` が入っている招待は明示的なエラーで拒否（使われた後の取り消しは無意味）
  4. `revoked_at = now()` / `revoked_by = 呼び出し者` を設定

🔴 **いずれも `SET search_path = ''` を付ける**（関数ハイジャック対策。既存の `current_member_*` 関数と同じ流儀）。
🔴 **NULL猶予条項を書かない**（2026-06-26の事故の教訓。Section 1.6）。
🔴 **ドル引用タグは関数ごとに区別する**（`$fn_create_project_invite$`/`$fn_accept_project_invite$`/`$fn_revoke_project_invite$`）。

## 7. 画面

- **ログイン画面**に「プロジェクトの招待コードをお持ちの方」の導線を追加（既存のログインフォームとゲストボタンの間）
- 招待コード＋メールアドレス＋氏名＋パスワードで登録
- サインアップ済みだが `members` 未登録の場合に出る `AccessDeniedScreen` にも、招待コード入力への導線を置く
- **発行側**：PJから「このPJに招待する」→ 相手のメールアドレスを入力 → コードとリンクが表示される（**1度だけ表示。再表示できない**）
- **管理画面**：招待一覧（誰が・誰を・どのPJに・いつ・使用済みか）と取り消し
